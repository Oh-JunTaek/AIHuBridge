## 1. 종합 판단

현재 프로젝트는 **기본 화면과 빌드는 갖췄지만, 공개 콘텐츠의 신뢰성과 자동 갱신을 먼저 보완해야 하는 단계**다.

현재 코드에는 외부 키를 사용하는 상용 뉴스 API 연동이 없고, 뉴스와 행사는 RSS로 수집하여 정적 JSON으로 제공한다. 무료 API 자체의 한계보다, 서로 다른 출처를 같은 방식으로 처리하고 미확인 정보를 확정값으로 채우는 구현이 문제다. 유료 API 도입이나 전체 재작성보다 기존 정적 구조를 유지하면서 데이터 계약·실패 처리·검증을 정비하는 편을 권장한다.

살릴 기반은 React·TypeScript 정적 앱, GitHub Pages 하위 경로 설정, 공식 출처 링크, 로컬 학습 체크, 난이도·분야 필터다. 우선 수정할 부분은 캘린더 정확성, 수집 실패 복구, 수집과 배포 연결, 오류 화면, 검증의 실효성이다.

## 3. 가장 먼저 고칠 문제

### P0-1. 캘린더가 실제 행사를 보증하지 못함

근거: `scripts/fetch-calendar.mjs:119` 이후 `rssItemToEvent`, `public/data/calendar.json`.

- 현재 14건 모두 신청 시작일 = 신청 마감일 = 행사 시작일이다. RSS 게시일을 세 필드에 그대로 복사한다.
- 14건 모두 `free`, `recruiting`으로 저장되어 있고, 기록된 마감일이 지났는데도 모집 중이다.
- `Hello world!`, `개인화 추천을 위한 랭킹 모델 개발기`, AWS 기술 글이 공모전·워크숍·웨비나로 분류된다. 출처별 고정 유형이 글의 실제 성격을 대신하고 있다.
- 온라인 여부는 출처 URL에 `zoom`이 있는지로 결정하며, 위치에는 기사 URL이 들어간다. 지역도 출처의 고정값이다.
- `confirmedAt`은 내용 검증 시각이 아닌 수집 실행 시각이다.
- 전체 수집 실패 시 실제 기관명·날짜·금액이 있는 샘플 2건을 일반 행사처럼 저장한다. 현재 JSON에 샘플은 없지만 다음 실패 시 발동할 수 있다.
- JSON 주소인 Devpost도 모든 다른 출처와 마찬가지로 RSS 파서에 전달한다. 출처 형식별 처리가 없다.

**보완:** 먼저 검증된 수동 행사 목록을 운영하고 자동 수집 결과는 검토 후보로 분리한다. 확인하지 못한 날짜·가격·장소·온라인 여부는 `unknown`/`null`로 유지한다. 실제 신청 공고와 일정 근거가 확인된 항목만 공개 모집 목록에 포함한다. 샘플은 개발용으로 격리하고 운영 데이터 대체에 사용하지 않는다.

**완료 기준:** 일반 기술 글과 샘플이 운영 행사로 표시되지 않음. 미확인 날짜에 D-day가 없고, 게시일·모집일·개최일이 구분됨. 수집 시각과 내용 확인일이 별도이며 상태는 날짜와 확인 정보로 산정됨.

### P0-2. 자동 갱신 결과가 배포까지 이어지지 않음

근거: `.github/workflows/refresh.yml`, `.github/workflows/deploy.yml`, `package.json`.

- `npm run refresh`는 뉴스와 캘린더를 모두 생성한다.
- 수집 워크플로의 `git add`에는 뉴스 JSON과 메타만 있다. 캘린더 JSON과 메타는 커밋 대상에서 빠져 있다.
- 수집은 기본 `GITHUB_TOKEN`으로 커밋·푸시하고 배포는 `push` 또는 수동 실행만 받는다.
- GitHub 공식 문서에 따르면 `GITHUB_TOKEN`으로 발생한 push는 새 push 워크플로 실행을 만들지 않는다. 현재 구성에는 이를 연결할 별도 단계가 없다. 실제 운영 실행 이력은 이번 조사에서 확인하지 않았다.
- 예약 실행에서 전체 selfcheck·빌드 없이 뉴스 총건수만 검사한다.

**보완:** 수집→검증→빌드→Pages 배포를 같은 워크플로의 명시적 단계로 연결하고 공통 빌드는 재사용한다. 추가 개인 토큰을 도입할 필요는 없다. 데이터 파일 4종을 하나의 갱신 묶음으로 취급하고, 수집과 일반 코드 배포 간 동시 실행·커밋 충돌 정책도 정한다. 실제 푸시·배포 실행은 사용자 요청 후 진행한다.

**완료 기준:** 수집 실행에서 생성한 데이터가 동일 빌드 산출물에 포함되고 공개 JSON까지 반영됨을 실행 로그·버전으로 입증. 실패 시 이전 공개 버전 유지.

### P0-3. 뉴스 수집 실패가 정상 데이터 소실로 이어질 수 있음

근거: `scripts/fetch-news.mjs:38-39`.

- 출처 실패는 빈 배열로 바뀌고, 최종 결과가 0건이어도 기존 파일을 덮어쓴다.
- 워크플로의 0건 검사는 커밋을 막지만 수집 스크립트 자체의 덮어쓰기를 막지는 못한다. 로컬 refresh에서는 기존 정상 데이터가 사라질 수 있다.
- 일부 출처만 실패해도 해당 출처의 기존 항목을 보존하지 않는다. 현재 메타에는 arXiv 0건이 기록되어 있으나 실패인지 정상 빈 피드인지는 알 수 없다.
- 기사 발행일이 없거나 잘못되면 현재 시각을 발행일로 넣어 최신순을 왜곡할 수 있다.
- ID 생성은 있지만 중복 제거는 없다. 현재 40개 URL은 서로 다르며, 실제 중복 발생을 확인했다는 의미는 아니다.

**보완:** 임시 결과 생성→런타임 스키마·품질 검사→정상 데이터 교체로 변경. 출처별 성공/실패/빈 피드/이전 데이터 사용 여부를 기록하고 제한된 재시도·백오프를 둔다. 이전 항목은 보존 기간과 stale 표시를 함께 적용한다. 발행일 미확인은 수집 시각으로 대체하지 않는다.

**완료 기준:** 전체 실패·일부 실패·정상 0건·깨진 응답을 각각 재현해 이전 정상 파일 보존과 오류 기록을 확인.

### P0-4. 화면이 로딩 실패를 ‘뉴스 없음’으로 숨김

근거: `src/lib/news.ts`, `src/pages/Home.tsx:16-38`, `src/pages/Research.tsx`, `src/main.tsx`, `src/pages/Dev.tsx`.

- `loadNews()`는 오류를 빈 배열로 반환하며 JSON을 타입 단언만 한다. 배열이나 필수 필드 검증이 없다.
- 홈은 요청 완료 전에 `setLoading(false)`를 실행하므로 로딩 중에도 빈 상태를 표시할 수 있다.
- 뉴스가 없으면 홈이 일찍 반환하여 오늘의 개념 등 다른 영역도 보이지 않는다.
- `/dev` 메뉴는 있으나 라우트가 없고 진단 메타 요청은 `/data/meta.json`이다.

**보완:** 공통 데이터 로더에서 loading/success/empty/error/stale을 구분하고 런타임 검증을 적용한다. 뉴스 영역에 재시도와 마지막 정상 수집 시각을 표시한다. 홈의 다른 영역은 독립적으로 유지한다. `/dev`는 공개 진단 페이지로 연결할지 메뉴를 제거할지 정책에 맞춰 정리한다.

## 4. 데이터와 기능의 품질 보완

### 뉴스: 수집 건수보다 원문 보존과 설명 품질

- 현재 뉴스 40건, 메타의 요약 분포는 LLM 0 / 규칙 40 / excerpt 0이다.
- 38건의 summary는 excerpt와 같고 16건은 title과 같다. 규칙 처리 성공 건수는 새로운 설명이 생성되었다는 뜻이 아니다.
- 규칙 요약은 앞 문장을 자르는 기능으로 한국어 번역이나 중요도 설명을 보장하지 않는다. 원문 발췌·규칙 요약·LLM 요약을 구분해 표시해야 한다.
- `src/lib/summary.ts`의 프론트 요약 함수는 호출하는 곳이 없다. README의 localStorage로 프론트 요약을 켠다는 안내는 현재 화면에 연결되어 있지 않다. 수집 스크립트의 Ollama 경로는 별도로 존재하며 이번에는 실모델 검증하지 않았다.
- 뉴스 출처가 `src/lib/config.ts`와 수집 스크립트에 중복 정의되어 Google AI/arXiv 등의 목록이 다르다.
- 제목 정리 함수는 짧은 한글 구절을 매체명으로 오인해 지울 가능성이 있다. 원제목과 표시 제목을 분리하고 알려진 출처명만 제거하도록 해야 한다.
- 카드에는 출처는 있으나 발행일·최종수집일 표시가 없다. ‘읽는 시간’은 원문이 아닌 RSS 발췌문 길이 기준이다.

권장 순서: 출처 설정 단일화→원문 필드 보존→날짜·출처·오래됨 표시→검색·태그 정규화→URL 중복 제거→선택적 요약 개선. 동일 이슈 자동 묶음과 한국어 생성 요약은 기본 신뢰성을 확보한 다음 단계로 둔다.

### 교육: 무료 수강과 무료 인증을 별도 정보로 관리

- 현재 `Certification`에는 수강료·수료증 발급료·시험료·지원 조건을 각각 표현할 필드가 없다.
- `costLabel()`은 가격 누락을 0으로 처리한다. `costKRW`도 표시 계산에 사용하지 않고 USD에 고정 비율을 곱한다. 미확인 값이 무료로 표시될 수 있다.
- 데이터의 `note`, `verifiedAt`, `freePrep` 등 중요한 조건이 현재 카드에 표시되지 않는다.
- 모든 항목의 검증일은 2026-10-21이지만 항목별 확인 근거는 없다. HTTP 200은 과정 실재·가격·무료 수료증 검증을 의미하지 않는다.
- 표본으로 확인한 Microsoft 공식 Azure AI Fundamentals 개요는 현재 AI-901을 요구 시험으로 안내한다. 저장소의 AI-900 항목은 공식 상세 정보와 대조해 갱신해야 한다. 16건 전부를 재검증한 것은 아니다.

권장 필드: 수강 비용 상태, 수료증 유무·발급 비용, 시험료, 국가·통화·지원 조건, 검증 출처, 내용 확인일, 모집/종료 상태. 우선 16건을 수동 재검증한 다음 검색·비교 기능을 붙인다. 로컬 완료 체크는 사용자 기록이며 기관의 공식 인증과 구별해 안내한다.

### 로컬 저장·기술 부채

- `src/lib/user.tsx`: 읽기는 예외 처리하지만 저장 실패는 처리하지 않음. 저장된 JSON의 필드 타입 검증·버전·이전 처리도 없음. 잘못된 배열 값은 여러 화면에서 오류를 낼 수 있다.
- 이전 영어 설정 값이 저장되어 있어도 한국어 전용 스키마로 정규화하지 않는다. 번역 키가 그대로 노출될 수 있다.
- 연속 방문은 날짜가 다르면 무조건 +1이며 방문 공백을 고려하지 않는다. 날짜 기준도 UTC이므로 한국시간 자정과 다르다. 기능 재노출 전에 수정 필요.
- 화면에서 숨긴 개인화 기능의 주석 블록, 사용되지 않는 프론트 요약·Dev 경로, 실제 사용 여부가 불분명한 타입·의존성을 정리할 필요가 있다.
- 루트의 `tmp-fix.cjs`, `write-calendar.cjs`는 수집 코드를 문자열 치환하는 임시 도구이고 `2`는 깨진 인코딩의 과거 검사 출력이다. 현행 기능 검증 후 제거 후보로 분류한다.
- 실제 라우터는 v7인데 v5용 `@types/react-router-dom`이 남아 있다. 필요성 확인 후 제거 후보로 둔다.
- 수집/배포의 Node 버전이 20/22로 나뉘어 있다. 검증된 하나의 버전과 package engines로 통일한다.

## 5. 검증 체계가 현재 놓치는 것

`npm run lint`는 이름과 달리 `tsc --noEmit`만 실행한다. 타입 검사는 유효하지만 코드 스타일·React 동작 규칙·접근성·데이터 의미 검사는 수행하지 않는다.

`selfcheck`는 현재 다음을 놓친다.

- 캘린더 JSON/메타 전체, 날짜 의미·요금·실제 행사 여부.
- URL의 안전한 스킴·실제 접근 상태, 발행일 유효성·미래 시각, 카테고리·태그 타입.
- 학습 경로의 실제 참조 대상 존재 여부. 현재는 파일에 `refId` 문자열이 있는지만 검사.
- 브라우저 라우팅·하위 배포 경로·오류/로딩 상태.
- 뉴스와 메타의 동시 갱신, 출처 실패율·오래된 데이터.

별도의 테스트 파일은 추적 파일 목록에서 찾지 못했다. 테스트를 늘리더라도 UI 구현을 그대로 복사하는 검사보다 **데이터가 잘못 안내되는 실패 사례**를 우선 자동화해야 한다.

핵심 회귀 사례: 전체 RSS 실패, 일부 출처 실패, HTML/잘못된 JSON 응답, 일반 글의 행사 오분류, 미확인 마감일, 마감 직전·직후, 한국시간 자정, 무료/가격 미확인, 손상된 로컬 저장, `/AIHuBridge/` 경로와 주요 메뉴 진입.

## 6. 무료 운영 구조 권고

기존 RSS·정적 JSON·GitHub Actions·GitHub Pages 구조를 유지한다. 외부 계정·키를 추가하거나 API 제공처를 늘리는 작업은 현재 우선순위가 아니다.

1. 뉴스는 승인된 RSS 목록, 교육·행사는 검증된 수동 목록을 기본으로 시작한다.
2. 각 수집원에 형식, 출처 주소, 제공 조건 확인일, 담당 파서, 타임아웃, 실패 정책을 정의한다.
3. 공통 정규화 스키마에 원문·수집 시각·내용 확인일·정보의 확인 상태를 담는다.
4. 수집 결과는 임시 후보로 만들고 스키마·품질 검사를 통과한 뒤 공개 JSON에 반영한다.
5. 동일 결과를 빌드·배포에 사용하고 공개 데이터 버전으로 반영 여부를 확인한다.
6. 브라우저는 정적 데이터만 읽고 loading/error/empty/stale을 명확히 표시한다.

RSS가 없거나 구조가 불안정한 기관은 수동 갱신 대상으로 두어도 된다. 초기에는 출처 수와 카드 수보다 확인 가능한 콘텐츠를 우선한다. Ollama는 개발자의 선택적 사전 생성 작업으로 제한하고 서비스 이용자의 PC에서 자동 제공되는 기능처럼 안내하지 않는다.

## 7. 권장 실행 순서와 인수 기준

| 순서 | 작업 묶음 | 완료 기준 |
|---|---|---|
| 1 | 행사 정확성 복구 | 샘플 격리, 일반 글 배제, 미확인 필드 도입, 검증된 행사만 공개 |
| 2 | 수집 보존·검증 강화 | 전체/일부 실패 회귀 검사, 이전 정상 데이터 보존, 캘린더와 참조 무결성 검사 |
| 3 | 갱신→배포 연결 | JSON 4종 처리, 동일 데이터 버전 빌드, 중복 실행 제어. 원격 실행은 사용자 요청 후 |
| 4 | 로더·홈·라우팅 복구 | 정상/빈 상태/오류/오래됨 구별, 홈 독립 영역 유지, `/dev` 정책 해결 |
| 5 | 교육 데이터 재검증 | 16건의 공식 근거와 비용·수료 조건 확인, 미확인은 무료로 표시하지 않음 |
| 6 | 범위·문서·코드 정리 | 용어·퀴즈·개인화 정책 확정, 문서 일치, 임시 도구·중복 설정 정리 |
| 7 | 브랜드·모바일·탐색 개선 | 기존 화면과 계획의 차이 먼저 공유 후 공통 UI, 검색·비교·월간 달력 순차 적용 |

작업별로 작은 한국어 커밋과 결과 기록을 남긴다. 대규모 일괄 재작성이나 과거 버전 전체 복원은 필요하지 않다. 각 묶음의 완료 표시에는 실제 검증 결과를 연결한다.

## 8. 이번 실행 결과와 확인하지 않은 범위

| 검사 | 결과 | 해석 |
|---|---|---|
| `npm run lint` | 통과 | TypeScript 검사 |
| `npm run selfcheck` | 통과 | 뉴스 40건·인증 16건·용어 35개에 대한 기존 제한적 검사 |
| `npm run build` | 통과 | 58개 모듈, JS 372.08 kB / gzip 117.09 kB, CSS 32.49 kB |
| 빌드 경고 | 있음 | Tailwind 변환의 sourcemap 경고 1건. 빌드 실패는 아님 |
| `npm run dev -- --host 127.0.0.1` | 기동 확인 | Vite 준비 완료, `/AIHuBridge/` 주소 출력 |
| 개발 서버 HTTP | 통과 | 별도 임시 포트에서 홈·research·calendar HTML과 뉴스·캘린더 JSON 요청 모두 200 |
| 화면 동작·모바일·접근성 | 미검증 | HTML 200은 React 렌더·클릭 동작의 통과 판정이 아님 |
| 운영 Pages·예약 Actions | 미검증 | 이번 분석은 로컬 코드·설정 기준 |
| RSS 재수집·Ollama | 미실행 | 분석 중 기존 JSON 보존. 현재 출처별 접속 성공률·실모델 품질은 판정하지 않음 |
| 교육 링크 전체 사실 검증 | 미완료 | Microsoft 공식 개요 표본 대조만 수행. 전수 재검증은 후속 과제 |

소켓 접근이 제한된 환경에서는 일반 실행의 HTTP 요청이 실패하여, 같은 임시 실행 안에서 서버를 기동하고 읽기 요청 후 종료하는 방식으로 HTTP를 확인했다. 이는 프로젝트 결함으로 판정하지 않았다.
